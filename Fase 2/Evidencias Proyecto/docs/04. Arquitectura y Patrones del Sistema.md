## 1. Arquitectura Global

La aplicación no sigue un patrón canónico tradicional (como un MVC puro), sino que implementa una **Arquitectura Híbrida de Escritorio Guiada por Eventos**, estructurada en torno a un estado centralizado en memoria (RAM) y persistencia basada en archivos físicos.

El sistema funciona cargando la totalidad de los datos en memoria durante el arranque o bajo demanda, operando sobre copias desconectadas en la interfaz de usuario, y consolidando los cambios de vuelta al disco físico mediante escrituras atómicas en hilos secundarios.

**Flujo Arquitectónico Real:**

Plaintext

```
Usuario 
   ↓ (Interactúa)
UI (MainWindow / Módulos)
   ↓ (Consulta datos mediante Getters / Retorna .copy())
DataManager (Singleton / Estado Global en RAM)
   ↑ (Carga inicial asíncrona)
Workers (MainDataLoaderThread, etc.)
   ↕ (Lectura/Escritura)
ExcelWriter / pandas.read_excel
   ↕ (I/O Físico)
Archivos Excel (Local / Red)
```

**Desviaciones arquitectónicas confirmadas en el código:**

1. `ExcelReader` se salta al `DataManager` y lee directamente el disco para la función `compare_snapshot`.
    
2. `SharePointSyncWorker` bypassa las capas de escritura centrales y utiliza `openpyxl` de manera directa para inyectar celdas en el archivo físico.
    

## 2. Capas y Responsabilidades

Aunque el proyecto se divide físicamente en carpetas (`src/ui`, `src/core`), la separación lógica de responsabilidades es porosa.

- **Capa de Presentación (`src/ui/`, ver [[03_Vistas_y_Navegacion_UI]]):** Actúa como **Fat Controller (Controlador Pesado)**. No solo renderiza widgets, sino que coordina hilos (`CompareSnapshotThread`), maneja lógica de negocio (búsquedas globales, cálculo de KPIs por cliente en `GeneralModule`) y orquesta transacciones de guardado instanciando sus propios Workers de escritura.
    
- **Capa Core / Datos (`src/core/`, ver [[02_Motor_de_Datos_Core]]):** Centraliza la I/O, el estado en memoria y las validaciones de limpieza (`DataFrameFormatter`). Sin embargo, carece de una interfaz de mutación estricta (Setters formales), lo que permite que otras capas modifiquen su estado interno.
    
- **Capa de Persistencia:** Delegada enteramente a librerías de terceros (Pandas y Openpyxl) orquestadas por un mecanismo propio de archivos temporales (UUID) y volcados mediante `os.fsync` para garantizar la atomicidad en Windows.
    

**Invasión de responsabilidades:** La UI invade frecuentemente la capa Core al inyectar DataFrames directamente en el Singleton (`dm.df_master = df_actualizado`) en lugar de solicitarle al Core que actualice su propio estado.

## 3. Patrones Arquitectónicos Realmente Utilizados

La aplicación ensambla múltiples patrones de diseño operativos para resolver los problemas inherentes a interfaces de usuario bloqueantes.

|**Patrón**|**Evidencia en Código**|**Beneficio Actual**|**Problema / Riesgo**|
|---|---|---|---|
|**Singleton**|`DataManager.__new__` verifica `_instance`.|Mantiene una única fuente de verdad en RAM compartida por todos los módulos.|Fuerte acoplamiento global; cualquier módulo puede corromper el estado si se salta las reglas.|
|**Worker / Background Thread**|Uso extensivo de `QThread` (ej. `MainDataLoaderThread`, `SharePointSyncWorker`).|Previene el congelamiento de la GUI durante lectura/escritura pesada.|La implementación está fragmentada; cada módulo UI define sus propios hilos de guardado.|
|**Observer (Signals/Slots)**|`pyqtSignal` interconectando `WatchdogThread` -> `MainWindow` -> UI.|Permite comunicación asíncrona fluida entre hilos secundarios y el Main Thread de Qt.|Trazabilidad compleja; es difícil depurar qué señal disparó qué actualización.|
|**Lazy Loading**|`MainWindow._load_module` solo instancia la clase de la vista cuando se hace clic.|Reduce drásticamente el consumo de RAM inicial y acelera la carga.|Un error de inicialización en un módulo oculto solo se descubrirá en tiempo de ejecución al abrirlo.|
|**Optimistic UI / Pending Changes**|`PandasTableModel` usa `_edited_cells` para superponer visualmente valores antes de guardarlos.|Permite editar masivamente sin latencia de disco entre cada celda.|Si el guardado falla, la UI y el disco quedan desincronizados hasta forzar una recarga.|
|**Proxy / Delegación transparente (`__getattr__`/`__setattr__`)**|`ComercialModule` (`src/ui/comercial.py`) es un `QTabWidget` contenedor que envuelve la implementación real, renombrada `_ComercialModuleLegacy`, bajo la pestaña "Interfaz antigua (actual)"; agrega una segunda pestaña "Nueva interfaz" (en construcción, solo lectura, repinta datos ya cargados por `_ComercialModuleLegacy.df_base`) y reenvía transparentemente a `self.legacy` cualquier atributo/método no propio (`table`, `model`, `load_data`, `pending_changes`, `confirm_save`, etc.) vía `__getattr__`/`__setattr__`/`__delattr__`.|Permite introducir una UI nueva en paralelo sin tocar ni duplicar la lógica de `_ComercialModuleLegacy`; `MainWindow` y los tests que instancian `ComercialModule()` siguen funcionando sin cambios.|Es el único módulo con esta indirección; añade una capa de reenvío de atributos que puede ser difícil de rastrear si se olvida su existencia al depurar.|
|**Envoltura global de un método de Qt (01-10-2026)**|`src/theme/tema.py` reemplaza `QWidget.setStyleSheet` por `_set_style_sheet_tematizado`, que convierte cada hoja a colores oscuros cuando el modo oscuro está activo; `GestorTema` (singleton) aplica el tema y emite `tema_cambiado`.|Da modo oscuro a toda la app sin reescribir los cientos de `setStyleSheet` con colores fijos.|Cambia el comportamiento de un método de Qt para toda la app, lo que no es evidente al leer cada módulo. Solo cubre llamadas hechas desde Python. Los widgets dibujados a mano deben pedir sus colores a `tema.fondo`/`tema.texto` o no cambian. Detalle en [[03_Vistas_y_Navegacion_UI]] §5.|

**Conclusión de Patrón General:** El sistema **no es MVC, ni MVVM, ni MVP**. Opera bajo un modelo de **Store Global Centralizado** (similar a Redux en web, pero sin inmutabilidad estricta), donde las vistas se suscriben a señales y leen/escriben sobre un estado compartido.

## 4. Dependencias entre Componentes

El acoplamiento estructural es predominantemente descendente, pero existen dependencias implícitas y bidireccionales a nivel de estado.

**Relaciones de Acoplamiento Fuertes:**

- **UI ─────→ Core (Dependencia Directa):** Todos los módulos importan `DataManager` y las constantes (`COL_VIN`, `COL_CHASIS`). Si se altera el nombre de una columna en `constants.py` o en el Excel, los DataFrames cambian y la UI se rompe silenciosamente.
    
- **UI ─────→ FileSystem (A través de ExcelWriter):** La UI no usa un repositorio abstracto para guardar; invoca a `ExcelWriter().update_cells()` inyectando los diccionarios formateados que Openpyxl necesita.
    

**Dependencias Inteligentes (Desacopladas):**

- **FileWatcher ──(Signals)──> MainWindow:** El `WatchdogThread` no sabe qué hacer con los datos; simplemente emite `file_changed_signal`. Es la ventana principal la que decide orquestar la comparación y notificar al usuario.
    

## 5. DataManager como Núcleo Arquitectónico

`DataManager` (documentado en detalle en [[02_Motor_de_Datos_Core]]) no actúa como un patrón _Repository_ tradicional, ya que no abstrae la tecnología de almacenamiento subyacente (devuelve estructuras nativas de Pandas).

Actúa como un **Store de Estado Global en Memoria (Cache Central).**

- **Por qué funciona:** Al cargar el Excel completo en la RAM una sola vez, permite que módulos como _Comercial_, _Operaciones_ o _Correos_ realicen filtrados locales ultrarrápidos (`get_comercial_df()`, `get_operaciones_df()`).
    
- **Fuente de Verdad:** Funciona como fuente de verdad _para la UI_, pero el disco físico sigue siendo la fuente de verdad del sistema.
    
- **Problema Arquitectónico Crítico:** El sistema sufre de **Múltiples Fuentes de Estado Mutables**. Cuando un módulo UI guarda datos con `ExcelWriter`, inyecta la porción modificada de regreso al `DataManager` para evitar recargar todo el Excel. Si esta inyección manual difiere de lo que realmente escribió `Openpyxl` en el disco, la aplicación pierde integridad hasta su próximo reinicio.

## 7. Flujo Arquitectónico: Modificación Externa (Auto-Heal)

El sistema brilla en su resiliencia ante cambios exógenos, un flujo arquitectónico altamente maduro (ver el detalle técnico completo en [[05. Flujos de Datos y Sincronización]] y [[06. Seguridad, Integridad y Resiliencia de Datos]]):

1. **Evento Externo:** Usuario de negocio modifica el archivo directo en SharePoint.
    
2. **Detección:** `WatchdogThread` detecta el cambio en el OS.
    
3. **Filtro Silenciador:** Descarta el evento si hubo un guardado propio hace menos de 30 s, o si hay uno en curso (`is_app_saving`) desde hace menos de 300 s. Si no, emite la señal (actualizado 28-09-2026, ver [[06. Seguridad, Integridad y Resiliencia de Datos]] §5).
    
4. **Comparación (Background):** `MainWindow` instancia `CompareSnapshotThread` -> `leer_datos_principales()` lee y limpia el Excel una vez -> `ExcelReader.compare_snapshot_desde_df()` cruza contra `data/cache/snapshot_comercial_<hash>.pkl` -> la lectura queda como precarga para la recarga siguiente (actualizado 28-09-2026).
    
5. **Auto-Heal:** Si `ExcelReader` detecta más de 200 cambios, deduce una corrupción de formato, sobrescribe el caché en silencio y aborta la alerta para no espantar al usuario.
    
6. **Resolución:** Si son cambios reales, se notifica al usuario mediante un Badge rojo. Si el usuario acepta, se invoca `DataManager.load_data_async()` para repoblar la RAM.
    

## 8. Concurrencia como Decisión Arquitectónica

La concurrencia no es un framework transversal centralizado, sino una **estrategia de delegación distribuida**.

En lugar de tener un "Command Bus" asíncrono en el Core, **cada módulo UI crea y administra sus propios QThreads** bajo demanda.

- `MainWindow` dispara `MainDataLoaderThread`.
    
- La interacción con SharePoint dispara `SharePointSyncWorker`.
    
- El silenciador de eventos simultáneos está rudimentariamente gestionado por las variables `save_timestamp` (freno temporal de 10 segundos para el Watchdog).
    
- **Problema:** Al estar orquestada por cada vista, si el usuario navega rápidamente entre módulos y dispara guardados simultáneos, no hay una cola de tareas (Queue) que serialice las escrituras. El disco podría ser golpeado por dos hilos a la vez (riesgo de colisión mitigado solo por el manejo de `PermissionError` en `ExcelWriter`).
- **Nota (07-09-2026):** `contactos.py` mitigó dos casos puntuales de este problema dentro de su propio módulo — un guard (`_empresas_loading`) evita instanciar un segundo `PowerBiSyncWorker` mientras el anterior sigue corriendo, y `table_plat.setEnabled(False)` evita una segunda eliminación mientras la primera no termina. Es una mitigación local, no la cola de tareas centralizada que este problema arquitectónico seguiría necesitando a nivel de sistema.
- **Mitigación a nivel de aplicación, no de módulo (sistema previo, confirmado en el código actual):** `FileLockMonitor`/`AppLockCoordinator` (`src/core/`, ver [[03_Vistas_y_Navegacion_UI]] §7.2) son un mecanismo distinto de los dos anteriores: en vez de evitar que un mismo módulo lance dos workers propios, `MainWindow` los arranca una sola vez para toda la aplicación y deshabilitan **toda** la interfaz mientras alguno de los 4 archivos maestros principales esté confirmado ocupado (sondeo cada 5 segundos, con banner rojo visible). No resuelve el problema de fondo descrito en este punto (seguir sin una cola de escrituras centralizada); es una capa distinta, orientada a que el usuario no intente editar mientras un archivo está bloqueado por otro proceso — ver el matiz sobre sus límites en §12 de este mismo documento.
    

## 9. Persistencia como Decisión Arquitectónica

El uso de **Excel + Pandas + Openpyxl** actuando como Base de Datos es una decisión arquitectónica pragmática y adecuada para un entorno corporativo interno como Empresa Demo, donde las barreras de infraestructura (solicitar servidores SQL, VPNs, despliegues IT) ralentizan la innovación de los equipos operativos.

- **Ventajas en el contexto real:** La información es inherentemente portable. Si la aplicación falla, el usuario de negocio (ej. Ejecutivo Comercial) simplemente abre el Excel y sigue trabajando. Existe confianza inmediata en el dato.
    
- **Desventajas:** Bloqueos a nivel de sistema operativo (`PermissionError` cuando SharePoint sincroniza). Las lecturas completas penalizan el arranque.
    
- **Escalabilidad:** Muy baja en términos de concurrencia de usuarios, pero perfectamente adecuada si el volumen de datos se mantiene en unos pocos miles de registros (actualmente mitigado por los respaldos y archivos temporales UUID).

## 10. Fortalezas Arquitectónicas

1. **Escudo de Archivos Temporales (Atomicidad):** `ExcelWriter` crea clones con `uuid4`, los modifica y luego utiliza `os.fsync` antes de sobrescribir el maestro (`shutil.copy2`). Esto previene contundentemente la corrupción de Excel ante cortes de energía o cierres forzados.
    
2. **Aislamiento de la UI:** A pesar del acoplamiento interno, el Main Thread de Qt rara vez sufre caídas de _framerate_ transaccionales gracias a los Background Workers.
    
3. **Filosofía Offline-First / RAM-First:** El sistema asume que el disco es lento y peligroso; hace el trabajo duro en memoria y toca el disco lo menos posible, un diseño robusto para redes inestables o OneDrive/SharePoint local.

|**Mutación de Estado Global**|Vistas actualizan `DataManager.df_master` sin métodos validadores.|Arquitectura carente de _Setters_ o de un patrón inmutable.|Divergencia silenciosa entre lo que el usuario ve en pantalla y lo que realmente hay en el disco.|**Alta**|

## 12. Riesgos Arquitectónicos Futuros

- **Aumento de volumen de datos:** Si el Excel comercial supera los 20.000 registros, el método `.compare_snapshot()` cruzando DataFrames iterativamente congelará los hilos de fondo por un tiempo excesivo. La interfaz "Auto-Heal" colapsará bajo su propio peso matemático.
    
- **Concurrencia Multi-Usuario Activa (mitigada parcialmente, sistema previo a esta revisión):** Si más de dos usuarios con la aplicación instalada guardan simultáneamente en una unidad de red o SharePoint sincronizado, la falta de control de concurrencia pesimista (Row-level Locking) causará sobre-escrituras masivas, borrando el trabajo del otro. El sistema actual asume un "Último en escribir gana" **como regla de fondo**, pero desde antes de esta revisión existe `FileLockMonitor`/`AppLockCoordinator` (`src/core/file_lock_monitor.py`, `src/core/app_lock_coordinator.py`; ver [[03_Vistas_y_Navegacion_UI]] §7.2): sondea cada 5 segundos si alguno de los 4 archivos maestros principales (Registro Maestro, Provisiones, BBDD Clientes CM, Administradores de Contactos) está confirmado ocupado, y en ese caso `MainWindow` deshabilita toda la interfaz y muestra un banner de bloqueo hasta que se libera. **Esto no resuelve el riesgo por completo, y el propio código lo reconoce explícitamente**: con el stack actual (sin Microsoft Graph/Entra) es imposible distinguir con certeza "otro usuario tiene el Excel abierto" de "OneDrive/SharePoint está sincronizando de forma transitoria" — el monitor nunca identifica al usuario, solo informa un booleano ocupado/disponible por archivo. El riesgo de "Último en escribir gana" sigue vigente para cualquier ventana de tiempo fuera de esa detección (ej. el archivo se libera justo antes de que dos personas guarden casi al mismo tiempo) y para cualquier archivo fuera de esos 4 vigilados.
    
- **Agregación de Nuevas Fuentes de Datos:** Integrar una API REST obligaría a refactorizar fuertemente los Módulos UI, ya que asumen que la respuesta siempre será un DataFrame tabular para inyectar en su `CustomTable`.

|**Atributo**|**Evaluación**|**Evidencia**|

## 14. Clasificación Final de la Arquitectura

Técnicamente, el sistema actual se clasifica como una **"Aplicación Monolítica de Escritorio basada en Eventos, estructurada en Capas Lógicas porosas (Fat UI), respaldada por un Store Global en Memoria y almacenamiento de Archivos Físicos mediante rutinas Atómicas concurrentes (Workers)".**

Su patrón principal de manipulación de datos sigue una arquitectura de _"Leer masivamente en RAM -> Editar Desconectado (Pending Changes) -> Sincronizar hacia archivo -> Reinyectar a RAM"_.

## 15. Conclusión

La arquitectura actual es sumamente **pragmática, coherente y excepcionalmente adecuada para el contexto inicial del problema**: digitalizar y controlar flujos corporativos sin depender del área de infraestructura para levantar bases de datos transaccionales. El esfuerzo arquitectónico invertido en mecanismos de resiliencia (Backups automáticos, Watchdog con silenciadores, Snapshots deductivos y temporales `fsync`) demuestra una profunda comprensión de los fallos estructurales del I/O en entornos Windows/SharePoint.

Sin embargo, el sistema ha alcanzado el límite de su deuda arquitectónica en el plano de la **separación de responsabilidades**. Para evolucionar, será perentorio consolidar el acceso a datos.

**Elementos a mantener ante una evolución:**

- El patrón _Pending Changes_ en las tablas (excelente experiencia de usuario).
    
- El blindaje de I/O mediante UUID y backups rotativos.
    
- El uso del `DataManager` en RAM para lecturas ultrarrápidas de la UI.
    

**Elementos críticos a refactorizar eventualmente:**

- Eliminar el acceso de escritura directo a las variables del `DataManager` por parte de las Vistas, implementando métodos estrictos de inyección/recarga (`Commands` / `Mutations`).
    
- Centralizar todos los _Workers_ de escritura bajo una única cola (Queue) en el Core, evitando que los Módulos UI disparen transacciones paralelas no coordinadas al disco.
