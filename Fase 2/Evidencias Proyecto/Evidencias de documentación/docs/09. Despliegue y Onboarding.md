Este documento responde una pregunta práctica: **si otra persona recibe este proyecto mañana, ¿cómo lo instala, configura, ejecuta y compila?**

Todo lo aquí descrito está verificado contra archivos reales del repositorio (`requirements.txt`, `exe.bat`, `debug.bat`, `config/settings.py`, `app_config.example.json`). No se documentan pasos ni herramientas que no existan en el proyecto.

## 3. Configuración

### Obligatoria

Definida en `app_config.json` (raíz del proyecto, no versionado — `app_config.example.json` es la plantilla). Si el archivo no existe, `config/settings.py` lo crea automáticamente con valores vacíos (`DEFAULT_CONFIG`) la primera vez que se ejecuta la app — ver [[01_Arranque_y_Configuracion]] §4.2.

| Clave | Uso |
|---|---|
| `DATA_DIR` | Carpeta de datos (06-10-2026). Las rutas de abajo que estén vacías se completan con ella y los nombres estándar de `config/rutas.py`; una ruta definida a mano tiene prioridad. Se fija desde Configuración → "Carpeta de datos" o con el asistente de primer arranque |
| `EXCEL_PATH` | Base comercial maestra (`RM_CONTRATOS.csv` desde el 13-10-2026; antes `PruebasFM.csv`, desde el cutover del 23-09-2026, y antes `PruebasFM.xlsx`, ver RG-41 en [[13. Matriz de Requerimientos y Trazabilidad]]). Acepta indistintamente `.xlsx` o `.csv`: todo el pipeline de lectura/escritura bifurca por la extensión real |
| `PROVISION_EXCEL_PATH` | Base de provisiones |
| `INSTALACIONES_PATH` | Reporte consolidado de instalaciones |
| `RM_REPORTE_PATH` | Maestro externo para sincronización comercial (se elige en Configuración → Avanzado, solo en modo programador) |
| `POWERBI_EXCEL_PATH` | Base de clientes de Power BI (`BBDD CLIENTES CM.xlsx`) |
| `CONTACTOS_EXCEL_PATH` | Directorio de contactos |
| `CORREOS_EXCEL_PATH` | Repositorio usado por las funciones de correo |
| `DELETED_LOG_EXCEL_PATH` | Papelera de eliminados |
| `LOG_EXCEL_PATH` / `LOG_CSV_PATH` | Historial de modificaciones (el `.csv` es el oficial vigente; ver [[06. Seguridad, Integridad y Resiliencia de Datos]] §8) |
| `CASOS_BAJA_CM_PATH` | Persistencia de `CasosBajaCM.csv` (casos de revisión de contratos CM, ver [[07. Procesos y Reglas de Negocio]] §4) |
| `EJECUTIVOS_PATH` | Directorio de ejecutivos (`Ejecutivos_VC.csv`, opcional; ver [[07. Procesos y Reglas de Negocio]] §11) |

`config/settings.py` deriva automáticamente en memoria `LOG_CSV_PATH` y `CASOS_BAJA_CM_PATH` si faltan en `app_config.json` (a partir de `LOG_EXCEL_PATH` y del directorio de `EXCEL_PATH`, respectivamente), sin reescribir el archivo real — ver [[01_Arranque_y_Configuracion]] §4.3.1.

**Modo programador (15-10-2026):** `MODO_PROGRAMADOR` en `config/settings.py` controla si Configuración muestra la pestaña **Avanzado** (archivo de referencia RM Reporte y sincronización RM_CONTRATOS). También se activa sin tocar el código con la variable de entorno `GESTOR_SSCC_PROGRAMADOR=1`. **Antes de generar el ejecutable con PyInstaller para el usuario común, la constante debe quedar en `False`.**

> **Clave huérfana (resuelta 06-10-2026):** `CUSTOMER_EXCEL_PATH` no la leía ningún módulo. Se eliminó del `app_config.json` real y `save_config` la descarta junto con `POWERBI_URL` (ver [[01_Arranque_y_Configuracion]] §4.3.2).

### Carpeta de datos del equipo (organización, 06-10-2026)

En la carpeta compartida del equipo los archivos que usa la aplicación viven juntos en una subcarpeta `datos/`: PruebasFM.csv, LogApp.csv, RegistroEliminado.xlsx, provisionContratos.xlsx, Instalaciones.xlsx, contactos.xlsx, Correos.csv, CasosBajaCM.csv, BBDD CLIENTES CM.xlsx, facturacionManual.xlsx, Historial_Envios_VC.csv y Ejecutivos_VC.csv (los dos últimos, junto con CasosBajaCM.csv, se derivan de la carpeta de `EXCEL_PATH`). `RM_REPORTE_CONECTADOS.xlsx` se queda en su carpeta de origen. Se eliminaron las copias antiguas (`PruebasFM.xlsx`, `Correos.xlsx`, `LogApp_incremental.csv`) y los `.snapshot_comercial*.pkl`: el snapshot de cambios ahora se guarda localmente en `data/cache`.

**Otro equipo:** si los archivos cambian de carpeta, el otro PC arranca con rutas que ya no existen; el asistente de primer arranque lo detecta, busca la carpeta nueva y deja todo configurado en un paso.

## 5. Ejecutar en desarrollo

Desde la raíz del proyecto, con las dependencias instaladas:

```
python main.py
```

`config/settings.py` detecta que no es un ejecutable congelado (`sys.frozen` es `False`) y calcula `BASE_DIR` como la raíz del proyecto, no la carpeta de un `.exe`.

Para correr la batería de pruebas automatizadas (`unittest`):

```
python src/tests/test_main.py
```

Esto genera datos mock, respalda y sobrescribe temporalmente el `app_config.json` real de la raíz, y lo restaura automáticamente al terminar. Ver detalle de los archivos de test en la sección 7 de `CLAUDE.md` (no forma parte del Vault de Obsidian).

### Auditor automático y sincronización de calidad (`duoc/calidad`)

Existe una segunda forma de correr la suite, con más información y un efecto adicional:

```
python src/tests/auditor/run_auditor.py
```

`src/tests/auditor/run_auditor.py` reutiliza el mismo `test_main.py::setup_sandbox()/teardown_sandbox()` (mismos datos mock, mismo respaldo/restauración de `app_config.json`), pero además descubre los `test_*.py` dinámicamente, mide duración y estado por test individual, cruza esa ejecución con un análisis estático (AST) de cada archivo, y escribe `src/tests/logs/AUDITORIA_DATA_<fecha>.json` / `AUDITORIA_RESUMEN_<fecha>.log`. Justo después de tener esos resultados — y antes de terminar — llama a `src/tests/auditor/quality_sync.py::sync(data, PROJECT_ROOT)`, que actualiza automáticamente los entregables de calidad en `duoc/calidad/`. Ejecutar `python src/tests/test_main.py` directamente **no** dispara esta sincronización: solo el auditor tiene los datos estructurados (docstring, clase, duración, clasificación por test) que `quality_sync` necesita.

Reglas de esta sincronización, verificadas contra el código de `quality_sync.py`:

- **Identidad de un test** = `(archivo, clase, método)` — ej. `test_comercial.py` + `TestComercial` + `test_buscar_vin`. Se lee parseando el texto que ya existía en las filas de los propios `.xlsx` (no hay ningún archivo de estado nuevo tipo `case_ids.json`).
- **`Reporte de Ejecución de Pruebas.xlsx`** funciona como snapshot de la última ejecución, no como historial acumulativo: un test ya conocido actualiza su misma fila (fecha/estado/duración); un test nuevo recibe el siguiente `CP-XXX` libre y una fila nueva. Los IDs ya publicados nunca se renumeran, aunque un test nuevo caiga alfabéticamente antes de otros ya existentes — esto es intencional y distinto del `case_id` interno transitorio que el propio auditor recalcula en cada corrida (`run_auditor.py::assign_case_ids`, global y alfabético), que nunca se usa como ID publicado.
- **`Casos de Prueba.xlsx`** agrupa por clase de test (una fila puede cubrir varios métodos). Una clase ya existente que gana métodos nuevos actualiza su misma fila (nunca crea una segunda); el rango de IDs solo fusiona números que de verdad pertenecen a esa clase, nunca rellena huecos con IDs de otras clases.
- **`Plan de Pruebas.docx`** y **`Plan de Gestión de Cambios.docx`**: la sincronización es deliberadamente limitada a los conteos 100% mecánicos ya soportados (cantidad de pruebas/archivos/clases, porcentaje de PASS de la última ejecución). Bullets descriptivos, cronograma de hitos y narrativa editorial nunca se generan ni modifican automáticamente.
- **`Request for Change (RFC).docx`** y **`Reporte de Defectos.docx`** permanecen bajo control manual: nunca se escriben automáticamente. Un `FAIL`/`ERROR` nuevo no crea un defecto — `quality_sync` solo compara contra el texto de los `BUG-XXX` ya redactados y avisa si coincide con uno conocido o si parece nuevo (`[QUALITY] ERROR conocido: BUG-001` / `[QUALITY] NUEVO FAIL/ERROR DETECTADO...`); confirmar y documentar un defecto real sigue siendo una decisión humana.
- **`duoc/calidad/_plantillas_originales/`** nunca se toca.
- **Escape hatch:** la variable de entorno `BRAND_SKIP_QUALITY_SYNC=1` desactiva únicamente esta sincronización (los tests y el reporte del auditor se generan igual).
- Cada corrida agrega/actualiza `src/tests/logs/QUALITY_SYNC_<fecha>.log` con el detalle de lo sincronizado, y los mismos eventos (prefijo `[QUALITY]`) se imprimen en consola.

## 6. Generar ejecutable

El proyecto incluye dos scripts `.bat` en la raíz, ambos basados en PyInstaller (`onedir`), y **no deben improvisarse comandos alternativos**.

### Producción — `exe.bat`

1. Limpia `build/`, `dist/` y `Gestor_SSCC.spec` si existen. **Actualizado (08-10-2026):** la aplicación pasó a llamarse **Gestor SSCC**; el ejecutable y la carpeta de salida usan ese nombre (antes `Dashboard_anterior`) y el acceso directo es `Iniciar Gestor SSCC.bat`. La carpeta del proyecto sigue llamándose `empresa_dashboard_app`.
2. Ejecuta:
   ```
   python -m PyInstaller --noconsole --windowed --onedir --clean --name "Gestor_SSCC" --icon="src/assets/app.ico" --collect-all PyQt6.QtWebEngineWidgets --collect-all qtawesome --collect-all openpyxl --add-data "src/assets;src/assets" main.py
   ```
3. Resultado: `dist/Gestor_SSCC/Gestor_SSCC.exe` — sin consola visible.

### Depuración — `debug.bat`

Mismo empaquetado (`--onedir --clean`, mismo ícono, mismos `--collect-all`), pero con `--console` en lugar de `--noconsole --windowed`, para ver la salida de consola (`print`, tracebacks) mientras se prueba el binario compilado.

**Diferencia clave entre ambos:** `exe.bat` es para distribuir a usuarios finales (sin ventana de consola); `debug.bat` es para diagnosticar problemas que solo aparecen en el binario empaquetado (no en `python main.py`).

Ambos scripts incluyen `src/assets` completo (`--add-data`) y fuerzan la recolección completa de `PyQt6.QtWebEngineWidgets`, `qtawesome` y `openpyxl`, necesarios porque PyInstaller no siempre detecta automáticamente sus recursos internos.

## 7. Instalación para el usuario final

**Distribución sin instalador (06-10-2026).** Ya no se usa el instalador que descargaba Python y las librerías. El ejecutable compilado es autosuficiente: se comprime la carpeta `dist/Gestor_SSCC/` en un `.zip` (el modo `--onedir` deja todas las dependencias junto al `.exe`, así que no se puede entregar el `.exe` suelto) y se deja en la carpeta compartida de SharePoint. La persona usuaria:

1. Descarga y descomprime el `.zip` en una carpeta local (no dentro de OneDrive).
2. Ejecuta `Gestor_SSCC.exe`. No necesita Python ni librerías.
3. Si no existe `app_config.json` junto al ejecutable, la aplicación lo crea con rutas vacías y, como `EXCEL_PATH` no existe, abre el **asistente de primer arranque** (`AsistenteRutasDialog`), que busca la carpeta de datos sincronizada y completa todas las rutas. El botón "¿Cómo me conecto?" abre la guía visual de 5 pasos.
4. Al confirmar, la app se reinicia ya conectada. Las URLs de Power BI/SharePoint se completan después en Configuración → Enlaces.
5. Tener Outlook instalado y configurado si va a usar el módulo de Correos.

El `.exe` se genera con los mismos parámetros de `exe.bat` (§6). Una actualización se entrega reemplazando la carpeta descomprimida; el `app_config.json` de cada persona se conserva si se copia o se deja fuera del reemplazo.

## 8. Problemas frecuentes

| Problema | Causa | Referencia |
|---|---|---|
| Aviso de "Error Crítico: No se encontró la Base de Datos" al abrir la app | `EXCEL_PATH` (u otra ruta obligatoria) vacía o apuntando a un archivo inexistente | `MainWindow._on_data_load_error` te dirige directamente a Configuración |
| Guardado rechazado / archivo bloqueado | El Excel está abierto por otro usuario o siendo sincronizado por SharePoint/OneDrive en ese instante (`PermissionError`) | La escritura aborta de forma segura sin tocar el archivo; ver [[06. Seguridad, Integridad y Resiliencia de Datos]] §4 |
| El Rescate de Contratos Huérfanos no encuentra el archivo de Notas de Venta descargado | El reporte exportado desde Power BI llega cifrado (IRM/Azure RMS); hay que abrirlo en Excel con sesión de Microsoft 365 activa y volver a guardarlo (`Ctrl+S`) antes de que la app pueda leerlo | [[05. Flujos de Datos y Sincronización]] §4.3 |
| `pip install -r requirements.txt` falla al parsear el archivo | Codificación UTF-16 detectada en `requirements.txt` (ver §2) | Reguardar el archivo en UTF-8 |
| No se puede compilar el `.exe` o falta un recurso al ejecutarlo | No se usó `exe.bat`/`debug.bat` tal cual, o falta alguno de los `--collect-all` | Usar los scripts existentes sin modificar los flags |
