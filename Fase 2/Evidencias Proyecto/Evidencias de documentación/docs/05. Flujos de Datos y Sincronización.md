## 1. Flujo de Carga Primaria (Lectura Inicial)

El flujo de lectura es el mecanismo estándar para alimentar la aplicación desde el disco hacia la memoria RAM.

**Secuencia confirmada:**

1. **Disparador:** La interfaz invoca `load_data_async()` o módulos específicos llaman a `load_contactos_async()`, etc.
    
2. **Worker:** Un QThread (ej. `MainDataLoaderThread`) lee el archivo físico. **Actualizado (23-09-2026, RG-41):** `MainDataLoaderThread` bifurca por extensión — `pd.read_csv(dtype=str, keep_default_na=False)` si `EXCEL_PATH` es `.csv` (caso real de producción desde el cutover), `pd.read_excel(sheet_name='BBDD (2)')` si es `.xlsx`. El resto del pipeline (pasos 3-5) es idéntico para ambos formatos.
    
3. **Prevención de Bloqueos:** En módulos críticos (Contactos), el Worker copia el archivo a `temp/ghost_contactos.xlsx` y lee desde la copia para evadir el `PermissionError` si SharePoint está sincronizando el original.
    
4. **Transformación y Limpieza:** El DataFrame crudo es inyectado a `DataFrameFormatter.clean()`. Aquí se validan columnas vitales (`VIN`, `CHASIS`), se recalcula la columna `TÉRMINO CONTRATO` basándose en `INICIO CONTRATO` + `DURACIÓN (MESES)`, y se estandarizan todas las fechas a `DD-MM-YYYY`.
    
5. **Inyección en RAM:** El Worker emite una señal (ej. `data_loaded_signal`) que el `DataManager` atrapa para actualizar sus atributos internos (ej. `self.df_master`).
    
6. **Consumo:** La UI solicita copias de seguridad mediante _Getters_ (ej. `get_comercial_df()`).
    

## 2. Flujo Transaccional Interno (Escritura Estándar)

Este flujo describe cómo se guardan las ediciones realizadas por el usuario en cualquier tabla del sistema.

**Secuencia confirmada:**

1. **Edición Local:** El usuario modifica una celda. El modelo `PandasTableModel` almacena la coordenada y el valor modificado en un diccionario `pending_changes` superponiéndolo visualmente en la UI.
    
2. **Disparador:** El usuario presiona "Guardar". Se invoca un QThread específico (ej. `SaveExcelThread`) pasándole el diccionario.
    
3. **Preparación I/O (`ExcelWriter`):** Se activa la bandera `DataManager.is_app_saving = True` y se registra el `save_timestamp`.
    
4. **Atomicidad:** Se crea un backup en `/data/backups/`. Luego, se clona el Excel a modificar en `/data/temp/` asignándole un identificador UUID.
    
5. **Escritura:** `Openpyxl` abre el archivo temporal, ubica la fila mediante las _Keys_ (ej. `VIN` o `AÑO - MES`), inyecta los valores nuevos y graba logs de auditoría.
    
6. **Volcado Físico:** Se utiliza `os.fsync` sobre el archivo temporal para forzar la escritura en el disco duro.
    
7. **Reemplazo y RAM:** El archivo original es reemplazado (`shutil.copy2`). Finalmente, el hilo retorna éxito y la UI actualiza su propia porción del `DataManager` en RAM sin tener que recargar el Excel completo.
    

## 3. Flujos de Integración y Cruce de Datos (ETLs Internos)

La aplicación implementa sincronizaciones cruzadas complejas donde un evento en un archivo modifica automáticamente otros.

### 3.1 Cruce Provisiones → Comercial

Cuando un usuario guarda cambios en el módulo de Provisiones, la aplicación actualiza automáticamente la base Comercial (reglas de negocio detalladas en [[07. Procesos y Reglas de Negocio]]).

- **Origen:** Diccionario de cambios pendientes en Provisiones.
    
- **Proceso (`SaveProvisionesThread`):**
    
    1. Guarda los cambios financieros en `provisionFelipe.xlsx`.
        
    2. Verifica si el `VIN` modificado existe en la RAM del `df_master` (Comercial).
        
    3. Construye un nuevo diccionario (`cross_updates`) calculando nuevos valores de `PERIODO INTERNO`, `TIPO DE SERVICIO`, `DURACIÓN (MESES)` y proyectando el `TÉRMINO CONTRATO` basándose en la fecha de inicio actual del camión.
        
    4. Ejecuta una segunda llamada a `ExcelWriter.update_cells` dirigida a la base Comercial.
        
- **Resultado:** Ambos archivos de Excel se actualizan secuencialmente y ambas secciones de la RAM se sincronizan. Si un `VIN` no existe en Comercial, se almacena como "huérfano" y se gatilla el flujo de rescate.
    
- **Separación UI/lógica (03-09-2026):** El paso 1 (normalización de `provisiones_changes`) y la conversión de `PERIODO INTERNO` dentro del paso 3 se extrajeron a `provisiones_services.construir_cambios_provisiones()`/`convertir_periodo_interno()`, funciones puras sin PyQt6, testeadas en `test_provisiones_services.py`. El resto del paso 3 (lectura de `INICIO CONTRATO` en `df_master` y la proyección de `TÉRMINO CONTRATO` vía `relativedelta`) se dejó **intencionalmente sin extraer**, dentro de `SaveProvisionesThread`: duplica `DataFrameFormatter.calcular_termino()` y no debía tocarse en esta refactorización.
    

### 3.2 Mega-Cruce Instalaciones (Sincronización de 4 Vías)

Genera el consolidado mensual de instalaciones para facturación cruzando todas las bases de datos.

- **Fuentes de Datos:**
    
    1. `df_prov` (Provisiones): Filtra únicamente los registros correspondientes al último mes.
        
    2. `df_comercial` (PruebasFM): Recupera CHASIS, RUT y CDB cruzando por `VIN`.
        
    3. `POWERBI_EXCEL_PATH` (Base David): Extrae Razón Social, Dirección y Comuna cruzando por `CDB`.
        
    4. `CONTACTOS_EXCEL_PATH` (Base Maxi): Extrae Nombres, Correos y Teléfonos cruzando por `CDB`, consolidando múltiples contactos en una sola cadena (ej. uniendo correos con `;`).
        
- **Transformación:** `InstalacionesSyncWorker` orquesta el cruce, calcula la fecha de término (`relativedelta`) y formatea los textos.
    
- **Salida:** Se genera una nueva pestaña en `Instalaciones.xlsx` nombrada dinámicamente (ej. "2026 - Julio").
    

### 3.3 Cruce Correos (`mail_sync_service.cruzar_correos_maestro`) — actualizado 03-09-2026

Genera `Correos.xlsx`, la base de destinatarios del módulo de envío masivo de correos (reglas de negocio detalladas en [[07. Procesos y Reglas de Negocio]] §8; flujo de UI en [[03_Vistas_y_Navegacion_UI]] §8).

- **Origen (separación UI/lógica, 03-09-2026):** Antes esta lógica vivía completa dentro de `CorreosSyncWorker` (`QThread` en `mail_dialog.py`). Ahora el Worker solo obtiene las tres fuentes (Comercial desde RAM vía `DataManager.get_comercial_df()`, Power BI y Contactos leídos de disco) y delega el cruce a `mail_sync_service.cruzar_correos_maestro(df_comercial, df_pbi, df_contactos)`, una función pandas pura sin dependencias de PyQt6, testeada en `test_mail_sync_service.py`.
    
- **Fuentes de Datos:**
    
    1. `df_comercial` (PruebasFM, desde RAM): base maestra — toda fila de Comercial se incluye en el resultado, tenga o no match en las otras fuentes.
        
    2. `POWERBI_EXCEL_PATH` (Base David): respaldo de Razón Social (campo `Nombre`) y RUT, usado únicamente cuando el dato de Comercial viene vacío. Se conserva un único registro por `CDB_MATCH` (el primero, tras deduplicar).
        
    3. `CONTACTOS_EXCEL_PATH` (Base Maxi): única fuente admitida para `CORREO ELECTRÓNICO`; no se deduplica — se concatenan con `"; "` todos los correos únicos asociados a un mismo CDB, ya que un CDB puede tener varios contactos registrados.
        
- **Actualizado (08-10-2026):** la clave de cruce de Comercial es `CDB FLOTA` y `POWERBI_EXCEL_PATH` ya no participa; la fuente 2 de arriba quedó solo por compatibilidad de firma. Sin `CDB FLOTA` en PruebasFM el cruce no corre (el diálogo avisa). La actualización puntual de §3.4 usa la misma columna. Ver [[07. Procesos y Reglas de Negocio]] §1.z y §8.

- **Clave de cruce (antes del 08-10-2026, `CDB`):** `CDB` normalizado (texto, sin sufijo `.0`, sin espacios, en mayúsculas), calculado como columna `CDB_MATCH` en Power BI y Contactos, y recalculado por fila en Comercial. La normalización de Comercial es levemente distinta a la de PBI/Contactos; no se unificó en esta refactorización.
    
- **Persistencia (`guardar_correos_excel`):** También extraída del diálogo hacia el servicio. Crea backup mediante `ExcelWriter._crear_backup()` (mecanismo existente, sin modificarlo); si el backup falla, cancela sin escribir nada. Si el backup es exitoso, escribe el DataFrame resultante con `df.to_excel()`. Nunca lanza excepción: devuelve `(ok, mensaje)` para que `SyncCorreosDialog.save_data()` decida qué `QMessageBox` mostrar.
    
- **Salida:** `Correos.xlsx` no conserva columna `CDB` propia — se calcula como `CDB_MATCH` durante el cruce y se descarta del DataFrame antes de persistirlo.
    

### 3.4 Actualización puntual de Correos (`contacto_correo_service.actualizar_correo_por_cdb`) — NUEVO, 03-09-2026

Corrige el correo de un solo CDB en `Correos.xlsx` sin rehacer el cruce completo, cuando el usuario da de alta un contacto desde `MailDialog` para una fila que no tenía correo asociado (detalle de UI en [[03_Vistas_y_Navegacion_UI]] §8).

- **Disparador:** Menú contextual "Agregar correo relacionado a esta empresa" sobre una fila sin correo en `MailDialog` → abre `ContactosAddDialog` con `cdb_prefill`/`flota_prefill` (CDB y Flota precargados y bloqueados, resto de campos editables) → al guardar, `MailDialog` agrega el contacto en `contactos.xlsx` mediante `ExcelWriter.add_new_row()` (mismo mecanismo que usa la pantalla Contactos) y recarga el caché de contactos vía `DataManager.load_contactos_async()`.
    
- **Recálculo:** `actualizar_correo_por_cdb(cdb, df_comercial, df_contactos, ruta_correos)` normaliza el CDB, filtra Comercial al subconjunto de ese CDB, y reutiliza `mail_sync_service.cruzar_correos_maestro()` sobre ese subconjunto (sin Power BI) para obtener el correo agregado actualizado — no reimplementa la regla de concatenación de correos, la invoca.
    
- **Escritura selectiva:** Construye un diccionario de cambios por `VIN` con solo la columna `CORREO ELECTRÓNICO`, y lo aplica con `ExcelWriter.update_cells(..., module_name="Correos", custom_filepath=ruta_correos)` — preserva el resto de columnas (CHASIS, Razón Social, RUT, Tipo de Servicio, Fecha de Término, etc.) y no toca filas de otros CDB.
    
- **Refresco:** `MailDialog._load_correos_file()` (el mismo mecanismo usado tras sincronizar) relee `Correos.xlsx` y repinta la tabla; la celda roja "SIN CORREO ASIGNADO" desaparece sin cerrar ni reiniciar la aplicación.

Los disparadores de guardado siguen siendo síncronos.

- **Aislamiento entre carriles:** ambas funciones de reconciliación filtran explícitamente por su propio `ORIGEN_CASO` en cada máscara; un mismo VIN puede tener un caso abierto en cada carril sin que se interfieran entre sí.

- **Ruta configurable:** `CASOS_BAJA_CM_PATH` en `app_config.json`, editable desde Configuración (ver [[01_Arranque_y_Configuracion]] y [[03_Vistas_y_Navegacion_UI]] §3). Ningún módulo la calcula ni la hardcodea.

## 4. Flujos de Sincronización con Entornos Externos

### 4.1 Extracción desde SharePoint (Nuevas Provisiones)

Extrae nuevos contratos desde un archivo de SharePoint sin utilizar APIs de red.

- **Extracción:** `SharePointSyncWorker` solicita la apertura de la URL en el navegador por defecto y escanea reiterativamente la carpeta "Descargas" de Windows buscando el patrón `Provision Contratos-RpySS*.xlsx`, con un timeout duro de 60 segundos (a diferencia de `EsperaReporteNVWorker`, que sondea hasta 600 segundos — ver más abajo); al vencer, lanza una excepción con un mensaje guiado pidiendo al usuario iniciar sesión en el navegador.
    
- **Deduplicación Estricta:** Construye una llave única combinando `AÑO - MES` + `VIN`. Cruza estas llaves contra la base local `provisionFelipe.xlsx` y filtra exclusivamente aquellas llaves que no existen localmente.
    
- **Inyección Física:** Abre el archivo local con `openpyxl`, añade las filas, y arrastra dinámicamente las fórmulas matemáticas (Monto Provisionado, Valor Plan, VAR) desde la fila superior utilizando `openpyxl.formula.translate.Translator`.

### 4.3 Autocompletado desde Notas de Venta (Rescate de Contratos Huérfanos)

Busca atributos comerciales faltantes para camiones nuevos o huérfanos detectados durante el cruce Provisiones → Comercial (`RescateDialog`/`RescateWorker` en `provisiones.py`).

- **Origen (actualizado 02-09-2026):** El reporte de "Notas de Venta" ya no se descarga desde SharePoint; ahora se obtiene desde un **reporte de Power BI** (`REPORTE_NOTAS_VENTAS_URL`), donde el usuario debe buscar manualmente el período antes de exportar. El archivo exportado (`Detalle*.xlsx`) llega protegido con **IRM/Azure Rights Management** (formato OLE2, streams `EncryptedPackage`/`DRMEncryptedDataSpace`, verificable con `olefile`) — ninguna librería de Python puede descifrarlo. El usuario debe abrirlo en Excel (con su sesión de Microsoft 365 autenticada) y volver a guardarlo (`Ctrl+S`) para que quede como `.xlsx` plano y legible por `pandas`.
    
- **Elección de fuente (`RescateDialog`):** El usuario puede elegir entre usar el reporte ya cacheado en `data/temp/temp_ventas.xlsm` o forzar la descarga de uno nuevo. Si el reporte cacheado no encuentra ninguna coincidencia, el sistema abre automáticamente el flujo de descarga en vez de terminar sin resultados.
    
- **Detección de descarga (`EsperaReporteNVWorker`):** Replica el patrón de `SharePointSyncWorker` ([[02_Motor_de_Datos_Core]] §7): abre la URL con `webbrowser.open`, limpia archivos `Detalle*.xlsx` previos en Descargas, y sondea la carpeta de Descargas hasta 600 segundos. Usa `zipfile.is_zipfile()` como gate de "archivo listo": distingue el `.xlsx` real (ZIP, ya descifrado por el usuario) del archivo IRM todavía protegido (OLE2), avisando al usuario si detecta el archivo pero sigue cifrado.
    
- **Copia a caché con reintento:** Al encontrar el archivo listo, se copia a `data/temp/temp_ventas.xlsm` mediante `_copiar_con_reintento` (reintentos con espera, 8×2s en el worker de fondo / 3×1s en el flujo síncrono de `RescateDialog`), para tolerar el `PermissionError` (`WinError 32`) que ocurre si el archivo sigue bloqueado por el SO/antivirus justo tras la descarga o el reguardado. La sincronización siempre prioriza el archivo de Descargas sobre el caché existente (ya no se compara por fecha de modificación, porque `shutil.copy2` conserva el `mtime` del origen y esa comparación resultaba poco confiable).
    
- **Cruce:** Se compara el `CHASIS` corto (últimos 7 caracteres del `VIN`) contra la columna `CHASIS` (o `Chasis`) de la hoja `Export` del reporte.
    
- **Salida — registro completo:** Si hay coincidencia, extrae RUT, `CLIENTE` (antes `RAZÓN SOCIAL`), Industria (normalizada vía `INDUSTRIA_MAP`), Vendedor y `TIPO` (antes `MODELO`), inyectándolos directamente en RAM/Excel local. Mantiene fallback a los nombres de columna antiguos por compatibilidad.
    
- **Salida — registro parcial (nuevo, 02-09-2026):** Si ni siquiera el reporte recién descargado encuentra coincidencia para un VIN, el sistema ya no descarta el dato: guarda el registro solo con `VIN`, `DURACIÓN (MESES)` y `TIPO DE SERVICIO` (los únicos datos que sí llegan desde Provisiones), marcándolo explícitamente como "REGISTRO PARCIAL (SIN NOTAS DE VENTA)" en el log de auditoría y notificando al usuario cuáles VIN quedaron incompletos.
    
- **Separación UI/lógica (03-09-2026):** Dentro de `RescateWorker.run()`, la detección de hoja/fila de encabezado, la búsqueda de la columna CHASIS, la normalización `CHASIS_CLEAN`, el matching VIN↔CHASIS, el mapeo de `INDUSTRIA` (`INDUSTRIA_MAP`) y la construcción de los registros completo/parcial se extrajeron a funciones puras en `provisiones_services.py` (`detectar_hoja_consolidado`, `detectar_fila_encabezado`, `encontrar_columna_chasis`, `normalizar_chasis`, `buscar_matches_por_chasis`, `mapear_industria`, `construir_registro_rescate_completo`, `construir_registro_rescate_parcial`), testeadas sin PyQt6. El worker conserva la lectura/escritura de Excel (`openpyxl`), el backup previo (`ExcelWriter._crear_backup`), las señales de progreso y la actualización de `DataManager`.
    
- **Decisión (02-09-2026) — Comercial y AddRecordDialog ya no procesan este reporte:** El antiguo "Autocompletar VIN" de Comercial (`_completar_vin_nv`) y la búsqueda de `AddRecordDialog` (`_search_in_notas_venta`) fueron **eliminados** en vez de migrados al nuevo formato de Power BI. En su lugar, Comercial tiene un botón circular "BI" que solo abre `REPORTE_NOTAS_VENTAS_URL` en el navegador para que el usuario consulte manualmente (filtrando por los últimos 7 dígitos del CHASIS/VIN dentro de Power BI); no hay lectura ni parseo de Excel desde Comercial ni desde AddRecordDialog. El procesamiento automático del reporte (lectura, normalización, matching por CHASIS) descrito arriba en esta sección sigue existiendo **únicamente** en Provisiones → Rescate de Contratos Huérfanos. Detalle en [[03_Vistas_y_Navegacion_UI]] §9.
    

### 4.4 Importación de unidades nuevas desde Power BI (`Detalle.xlsx`) — actualizado 06-10-2026

El Excel del reporte de Notas de Venta ya trae el VIN, así que la importación no pasa por el formulario unidad por unidad: `importar_powerbi.iniciar_importacion_power_bi` lee la hoja `Export` (`powerbi_import_service.leer_hoja_export`), arma los registros con `construir_altas_nuevas` y los escribe de una vez con `ExcelWriter.add_new_rows_batch` (un solo backup y una sola auditoría). ## 5. Detección Externa y Silenciamiento (Flujo Watchdog)

Cómo el sistema maneja la edición de los archivos de forma externa (ej. otro usuario modificando SharePoint).

Fragmento de código

```
graph TD
    A[Modificación en Excel Físico] --> B(FileWatcher)
    B --> C{¿Guardado propio hace < 30 s?}
    C -->|Sí| E[SILENCIAR EVENTO]
    C -->|No| D{¿is_app_saving y guardado iniciado hace < 300 s?}
    D -->|Sí| E
    D -->|No| F[Emitir Señal]
    F --> G[MainWindow: CompareSnapshotThread]
    G --> H[leer_datos_principales: una lectura + clean]
    H --> I[Compara con data/cache/snapshot_comercial_hash.pkl por VIN]
    H --> P[Guarda precarga en DataManager]
    I --> J{¿Cambios > 200?}
    J -->|Sí| K[Auto-Heal: Reconstruye snapshot en silencio]
    J -->|No| L[Registra un aviso en la campana y suma al círculo rojo]
    L --> R[load_data_async reutiliza la precarga si el mtime no cambió]
```

_Confirmado en el código: El silenciador protege a la aplicación de entrar en un bucle infinito de recargas cuando ella misma es la autora de la escritura en el disco_. Mecanismo completo (debounce + ventana de silencio, actualizado 28-09-2026) documentado en [[06. Seguridad, Integridad y Resiliencia de Datos]] §5.

**Notificaciones de la campana (actualizado 07-10-2026):**
- **Qué se compara:** `COLUMNAS_SNAPSHOT_COMERCIAL` (`excel_reader.py`) pasó de 22 a 30 columnas. Se agregaron RAZÓN SOCIAL, FECHA DE BAJA, ESTADO DE ENTREGA, PERIODO INTERNO, OBSERVACIONES, TIPO DE CM, FECHA INICIO CM y FECHA TERMINO CM. Además se corrigió `TIPO DE FACTURACION`: el código la buscaba con tilde, la columna real no la lleva, y por eso nunca se detectaba un cambio en ella. ETAPA GESTIÓN sigue fuera (es un cálculo derivado de otras columnas).
- **Primera comparación tras el cambio:** el snapshot guardado no tiene las columnas nuevas, así que la comparación ve miles de diferencias, supera el límite de 200 y se reconstruye en silencio (Auto-Heal) sin avisar. Es esperado.
- **Cómo se muestran:** `MainWindow._on_snapshot_finished` entrega los cambios a `PanelNotificaciones` (`src/ui/notificaciones.py`), que crea un aviso por tipo (unidades agregadas, modificadas, eliminadas), con hora y archivo de origen; el círculo rojo cuenta los avisos sin leer. Detalle visual en [[03_Vistas_y_Navegacion_UI]] §2.
- **Aviso tardío tras un guardado propio (corregido 08-10-2026):** el guardado de la propia aplicación no actualizaba la base de comparación, así que el siguiente cambio externo se comparaba contra un estado viejo y llegaba tarde. Ahora `MainWindow._actualizar_base_notificaciones_tras_guardado_propio` (con `ActualizarBaseNotificacionesThread` y `compare_snapshot_desde_df`) refresca esa base tras la recarga posterior a un guardado propio, dentro de la ventana de silencio. El clic en un aviso ya no cierra el panel: `notificaciones.py` acepta el evento de ratón para que no llegue al menú de la campana. El cierre del panel se corrigió por semántica de eventos de Qt y no se pudo reproducir sin ventana real.
- **Alcance conocido (sin cambios):** solo se vigila PruebasFM. Provisiones, Contactos, Instalaciones, Casos CM y los demás archivos no generan aviso ni se recargan solos cuando alguien los modifica por fuera. Un cambio externo dentro de los 30 s posteriores a un guardado propio no avisa (ver [[06. Seguridad, Integridad y Resiliencia de Datos]] §5), y una actualización de más de 200 cambios se trata como error de formato y no avisa.

## 6. Observaciones del flujo actual

- **Confirmado (Dependencia Fuerte de Red):** El cruce total de `InstalacionesSyncWorker` depende de que los archivos de "Contactos" y "Power BI" estén físicamente accesibles. Si la ruta de Power BI no se actualiza o desaparece, el flujo genera campos vacíos de Razón Social y Dirección.
    
- **Confirmado (Mutación del ID en Contactos):** Durante el flujo de Contactos, existe una lógica que convierte _Favoritos_ antiguos (basados en Correo y Nombre) a un ID permanente, garantizando que si el correo cambia, el contacto siga marcado. **Actualizado (07-09-2026):** el cálculo puro de esta migración vive ahora en `contactos_service.migrar_favoritos_legacy()`; `ContactosModule._migrate_pinned_contacts()` solo decide si aplicar el resultado y persistirlo (`save_pinned()`). Mismo comportamiento, sin cambios de regla.
    
- **Riesgo Futuro (Sincronización RM_JAVI):** El `RMJaviSyncWorker` realiza un `merge` completo (Left Join) con la base externa. Si el archivo `RM_JAVI` es vaciado por accidente en SharePoint antes de la sincronización, el flujo detectará los VINs como "eliminados" y los dará de baja en el Excel local masivamente.

- **Riesgo Confirmado (Sincronización RM_JAVI puede revertir imports más recientes):** `RM_JAVI_COLUMNAS_AUTORIZADAS` hace que RM_JAVI sea la fuente autoritativa de columnas como `ESTADO COMERCIAL`, `FORMA DE CONTRATO` y los 6 campos de CM (`N CONTRATO 3PC`, fechas, `TIPO DE CM`, `ESTADO DEL CM`, `PAGO CM`) — las mismas que actualiza el import masivo de Contratos CM (§7 de [[07. Procesos y Reglas de Negocio]]). Verificado por simulación (30-09-2026, sobre copias de `PruebasFM.csv` y `RM_JAVI_VOLVO CONNECT.xlsx` reales): si se sincroniza con RM_JAVI después de un import de Contratos CM, y el RM_JAVI real todavía no fue actualizado por Javiera con los mismos datos del 3PC, la sincronización revierte esos campos a sus valores anteriores (incluye perder el `ESTADO COMERCIAL="Revisar"` que el import acababa de marcar por vencimiento de CM). No hay ninguna protección hoy contra este orden de operaciones.

- **Dirección Futura confirmada por el usuario (30-09-2026, todavía NO implementada):** la sincronización con RM_JAVI se considera un mecanismo temporal. Lo que la app ya hace hoy (traer los datos de Javiera — 3PC de Contratos CM, Provisiones — hacia `PruebasFM.csv`) es el diseño correcto: la idea es cubrir ahí todos los casos posibles para dejarle el trabajo más fácil a Javiera. El día que Javiera empiece a usar la app directamente, `PruebasFM.csv` pasa a ser, literalmente, el mismo archivo que hoy se llama `RM_JAVI` — **solo cambia el nombre** (a `RM_JAVI.csv`), no hay migración de datos ni un escritor nuevo hacia el `RM_JAVI_VOLVO CONNECT.xlsx` externo (esa alternativa se planteó y el usuario la descartó por innecesaria). `RM_JAVI_VOLVO CONNECT.xlsx` como archivo separado deja de existir, y en ese momento `RMJaviSyncWorker` se deshabilita por completo (ya no habría dos archivos que mergear). Sin fecha confirmada — no implementar ni proponer este cambio salvo pedido explícito.

- **Riesgo Confirmado (Dependencia manual en Notas de Venta):** El flujo de descarga del reporte de Power BI (§4.3) depende de que el usuario reabra y reguarde manualmente el archivo exportado para descifrarlo (protección IRM/Azure RMS). Si el usuario no completa ese paso, `EsperaReporteNVWorker` agotará el timeout de 600 segundos sin detectar el archivo, y el Rescate de Contratos Huérfanos no podrá completarse hasta que se repita la descarga.
